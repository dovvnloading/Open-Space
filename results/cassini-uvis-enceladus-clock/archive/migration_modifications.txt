Cassini UVIS EUV/FUV Cruise PDS3-PDS4 Update Summary
====================================================

This bundle was migrated by the PDS Ring-Moon Systems Node from PDS3 to PDS4. 
Users can find the original EUV/FUV PDS3 labels in the Cassini UVIS volset at 
https://pds-rings.seti.org/viewmaster/volumes/COUVIS_0xxx.
Data files were not affected, and metadata available in the PDS3 volumes have 
been captured in the PDS4 bundle. Note, however, that during the migration:

    - Several errors in the PDS3 metadata were corrected (section 1), 
    - Products that were not relevant to PDS4 were omitted (section 2),

For those corrected products, we have included additional comments in their PDS4 labels. 

In addition, miscellaneous notes are included in section 3.


1. Corrections Implemented in the Migration to PDS4 
---------------------------------------------------

1a. **Timing Corrections**

The PDS3 labels do not report SPACECRAFT_CLOCK_STOP_COUNT (always "UNK",
meaning unknown). We calculated <cassini:spacecraft_clock_stop_count> in the 
PDS4 labels as a service to users, but we encourage users to check these calculations 
and contact us if there are any differences. Furthermore, we have found some 
discrepancies between the SPACECRAFT_CLOCK_START_COUNT and START_TIME values recorded 
in the PDS3 labels (details below).

The UVIS User's Guide, provided in the document collection, states:

  "the clock start is the Cassini clock time at the end of the first sample, the 
  start time is a text string corresponding to the spacecraft clock start time, the
  stop time is a derived value produced by multiplying the INTEGRATION_DURATION by
  the number of samples ..."

So we calculate the SCLK stop count using the PDS3 SCLK start count and the 
duration values:

  SPACECRAFT_CLOCK_STOP_COUNT = SPACECRAFT_CLOCK_START_COUNT + observation duration

where for a 1D spectrum, the observation duration is equal to the INTEGRATION_DURATION; 
for a 3D qube, the observation duration is equal to the INTEGRATION_DURATION*SAMPLE 
(where SAMPLE is given in the CORE_ITEMS entry of the PDS3 label).

The following steps were taken to calculate time values:

  - Using `cspyce` (https://github.com/SETI/rms-cspyce), import and furnsh two SPICE
    kernels: naif0012.tls and cas00171.tsc. Note that kernel 171 was chosen (rather 
    than the latest, 172) in order to test the internal consistency of timing in the
    data delivered in PDS3.
  
  - Calculate the SPACECRAFT_CLOCK_STOP_COUNT from the SPACECRAFT_CLOCK_START_COUNT and duration:
  
    def calculate_spacecraft_clock_stop_count(spacecraft_clock_start_count, duration):
          parts = spacecraft_clock_start_count.split('.')
          start_x256 = 256 * int(parts[0][2:]) + int(parts[1])
          stop_x256 = start_x256 + duration * 256  
          seconds = int(stop_x256 // 256)
          frac = int(stop_x256 - seconds * 256)
          spacecraft_clock_stop_count = f'{seconds}.{frac:03d}'
          return spacecraft_clock_stop_count  
    
    Each integer "tick" of the Cassini clock is one second, and the number after 
    the period is in units of 1/256 seconds.
    This value is provided in the PDS4 labels as <cassini:spacecraft_clock_stop_count>
  
  - Take the calculated <cassini:spacecraft_clock_stop_count> and convert the value 
    to ephemeris time (ET), then to UTC (using cspyce). This value is recorded in PDS4
    <stop_date_time> (equivalent to PDS3 STOP_TIME).
  
  - Take the PDS3 value for SPACECRAFT_CLOCK_START_COUNT and convert the value to 
    ephemeris time (ET), then to UTC. This value is recorded in PDS4 <start_date_time>
    (equivalent to PDS3 START_TIME).
  
  - Reformat the new value for <start_date_time> from yyyy-mm-ddTHH:MM:SS.SSSZ to 
    yyyy-dddTHH:MM:SS.SSSZ. This reformatted value is recorded in PDS4 <cassini:start_time_doy>.
    Likewise, reformat <stop_date_time>.

Some discrepancies were found between the calculated time values and those reported
in the PDS3 labels. That is, when comparing:
  - PDS3 START_TIME and PDS4 <start_date_time> 
  - PDS3 STOP_TIME and PDS4 <stop_date_time> 

To illustrate, consider the example of euv2000_364_09_23.lblx (note that the same 
method was used for both Saturn and Cruise bundles). The PDS3 label states:
  START_TIME                      = 2000-364T09:23:35.337
  STOP_TIME                       = 2000-364T11:38:55.337

However, we calculate the times (based on SCLK start count and observation duration
described above) to be:
  <start_date_time>2000-12-29T09:23:32.712Z</start_date_time>
  <stop_date_time>2000-12-29T11:38:52.656Z</stop_date_time>

Our calculated start time is 2.625 s earlier than the START_TIME delivered by the 
team to PDS3. Our calculated stop time is 2.681 s earlier than the STOP_TIME 
delivered by the team to PDS3. Therefore, our observation duration is 0.056 s shorter. 

As part of the PDS4 migration, analysis of the differences between the calculated 
<start_date_time> and PDS3 START_TIME, and the calculated <stop_date_time> and 
PDS3 STOP_TIME was performed over the entire time period covered by EUV/FUV 
observations. Across the dataset, the stop times have greater disagreement than 
start times. The majority of timing differences are under 1 second. 

However, there is a cluster of observations (for the Cruise bundle) with start 
times from mid-2000 to early-2002 that show 1 s < stop time differences < 2.7 s, 
for example:
  - EUV2000_364_09_23.LBL reports stop and start time differences >2.5 seconds.
    (FUV2000_364_09_23, reports a smaller time difference (<60 ms)).
  - EUV2000_258_20_48.LBL and FUV2000_258_20_48.LBL report stop time 
    differences >1.8 s, but no start time differences.

In this Saturn bundle, there is a larger cluster of observations with start times 
from early-2009 to late-2010, that have between 1 to 4 second start and stop time 
differences. There are two further clusters of observations with start times from 
mid-2012 to early-2015, and from early-2017 to EOM, that show start/stop time 
differences of about 1 second.

    START_TIME                      = 2006-341T18:59:57.698
    STOP_TIME                       = 2006-341T19:05:07.698
    INTEGRATION_DURATION            = 155.000 <SECOND>
    AXIS_NAME                       = (BAND, LINE, SAMPLE)

1c. **Target Identification**

1c.i. *Target Information Improvement*

In many cases, the PDS3 TARGET_NAME was incomplete. In some cases, the PDS3 
TARGET_NAME was abbreviated; these were replaced in the PDS4 labels with the 
corresponding full name. For the Cruise bundle, this was quite minimal: the 
PDS3 TARGET_NAME = "S RINGS" becomes "Saturn Rings" in the PDS4 label. In the 
Saturn bundle there were more instances of this, for example PDS3 TARGET_NAME = "DA" 
is identified as "Daphnis" in PDS4; TARGET_NAME = "ME" is identified as "Methone"; 
TARGET_NAME = "PO" is identified as "Polydeuces". In some PDS3 labels, Saturn's 
rings were not identified under TARGET_NAME but were described in the purpose of 
the OBJECT.DESCRIPTION; in those cases, the PDS4 Target_Identification includes 
"Saturn Rings".

1c.ii. *Using Timing Information to Identify Targets*

In some cases, target identification in PDS3 was incorrect and has been corrected 
during the migration to PDS4. This only affects this Saturn bundle (not the Cruise 
bundle), as the correction method relies on using the Cassini Time-Ordered Listing 
(TOL, a schedule of observations by all instruments), which only dates back to 2004, 
together with the CIMS (Cassini Information Management System) request IDs. 
The TOL is available at https://pds-rings.seti.org/cassini/Final-Cassini-TOL.txt. 
An explanation of CIMS requests, from https://pds-rings.seti.org/cassini/cirs/reform_about.html, 
is given below:

  "A CIMS request corresponds to a particular block of time in which one or more 
   instruments observe (usually) a single target. In the Cassini timeline, one 
   instrument is always "prime" and defines the details of the observation, such 
   as where the instrument points and how long it dwells at each location. Often, 
   additional instruments are 'riders' and will obtain simultaneous data from the 
   same target.

   CIMS requests have identifiers such as this:

   CIRS_016RE_E60PHASE001_VIMS

   It is constructed as follows:

   CIRS: Indicates the instrument doing the observation, regardless of whether it is prime or a rider.
   016: Indicates Cassini's orbit number
   RE: Abbreviation for the nominal target, in this case Ring E.
   E60PHASE: A brief mnemonic indicating the purpose of the observation, in this case to gather the phase curve information around 60 degrees.
   001: For the first activity of this type in the given orbit of Cassini.
   VIMS: Finally, this indicates that the VIMS (Visual and Infrared Mapping Spectrometer) instrument is prime for the observation. If CIRS had been prime, the identifier would have ended with PRIME instead.

  The CIMS request ID associated with a given file can be found in the PDS[3] label 
  as the value for the keyword OBSERVATION_ID."
  
The CIMS ID was key in helping identify targets that were "unknown" in PDS3. The 
PDS3 labels have 956 unknown stars (where TARGET_NAME = "STAR")

The following method was used to identify most of those unknown stars:

    1) A dictionary of star abbreviations was created to extract the star name 
       from the encoding used in the CIMS ID: 
       STAR_ABBREVS = {
                      '126TAU'   : ('126 Tauri'           , ['126 Tau'],                      '126_tau'),
                      ...
                      'IOTORI'   : ('Iota Orionis'        , ['Iota Ori'],                     'iot_ori' ), 
                      ...
                      'ZETPUP'   : ('Zeta Puppis'         , ['Zeta Pup'],                     'zet_pup'),
                      }

    2) The datetime of the observation was matched with the CIMS ID, e.g. for FUV2012_004_15_30.LBL: 
       "2012_004_15_30,UVIS_159ST_URIOTORI001_PIE"
       that is, obtained by using information from the TOL:

       "UVIS_159ST_URIOTORI001_PIE	UVIS_32096		2012-004T14:06:00		000T02:34:00	2012-004T16:40:00	7221.6	66.728	Prime	UVIS_HSP to 83.858/-5.91	NEG_X to NSP"	
       (that is, by checking where the observation in question, 2012_004_15_30, fell with respect to the time ranges described in the TOL).

    3) If the STAR_ABBREV was found in the CIMS ID (e.g. "IOTORI" in this example), then the name of that star is inserted into the PDS4 label, for example: 
        <Target_Identification>
            <name>Iota Orionis</name>
            <alternate_designation>Iota Ori</alternate_designation>
            <type>Star</type>
            <Internal_Reference>
                <lid_reference>urn:nasa:pds:context:target:star.iot_ori</lid_reference>
                <reference_type>data_to_target</reference_type>
            </Internal_Reference>
        </Target_Identification>

    4) The original PDS3 TARGET_NAME was preserved in the PDS4 label via 
       <cassini:pds3_target_name>STAR</cassini:pds3_target_name>.

to search the TOL, then the start and stop times of matches were used to find ISS 
primes in the COISS_2999 cumulative index table (available at 
https://pds-rings.seti.org/holdings/metadata/COISS_2xxx/COISS_2999) that fell 
within the observing times of UVIS riders. Then, since the rider can be assumed 
to be collecting simultaneous data from the target, the target identified in the 
ISS cumulative index was used in the EUV/FUV PDS4 labels. 

For example, for UVIS_046OT_OUTERSATS001_ISS, the TOL states:

"UVIS_046OT_OUTERSATS001_ISS	UVIS_5032		2007-165T21:17:00		000T01:00:00	2007-165T22:17:00	5032.0	18.115	SPASS Rider"

Searching for observations in COISS_2999_index.tab that most closely align with 
the TOL start and stop times indicates that Mundilfari was the ISS target. Then, 
since UVIS was riding along with ISS, the PDS4 label (fuv2007_165_21_39.lblx) states:
        
        <Target_Identification>
            <name>Mundilfari</name>
            <alternate_designation>Saturn XXV (Mundilfari)</alternate_designation>
            <alternate_designation>S/2000 S 9</alternate_designation>
            <alternate_designation>NAIF ID 625</alternate_designation>
            <type>Satellite</type>
            <description>
                NAIF ID: 625;
                Center of motion: Saturn;
                LID of central body: urn:nasa:pds:context:target:planet.saturn;
                NAIF ID of central body: 699.
            </description>
            <Internal_Reference>
                <lid_reference>urn:nasa:pds:context:target:satellite.saturn.mundilfari</lid_reference>
                <reference_type>data_to_target</reference_type>
            </Internal_Reference>
        </Target_Identification>

If it was not possible to glean information from the PDS3 TARGET_NAME, OBJECT.DESCRIPTION, 
or CIMS ID, then 'urn:nasa:pds:context:target:calibrator.unk' was used for the unknown target.

For many stellar occultations, only the occulted star is reported in the Target_Identification 
area of the label – the science target (e.g. Saturn, Titan) is missing. Check the 
Array_3D_Spectrum.description for details about targets. 

Users are encouraged to check the <description> of <File_Area_Observational> 
(OBJECT.DESCRIPTION in PDS3) for further details about the intended targets, as
well as the CIMS ID and timing information present in the Time-Ordered Listing 
and ISS cumulative index (available at https://pds-rings.seti.org/cassini/Final-Cassini-TOL.txt 
and https://pds-rings.seti.org/holdings/metadata/COISS_2xxx/COISS_2999/COISS_2999_index.tab, 
respectively). 

A comment has been placed in the affected PDS4 LBLX raw data labels in the 
<Observation_Area> class noting that a target correction was made. The original 
PDS3 TARGET_NAMEs are preserved via <Legacy_Metadata>.


1d. **Mission Phase Names Standardized** 

Values of `cassini:mission_phase_name` have been updated for consistency across 
instrument data sets. This is because different instruments specify the mission
phases in ways that diverge from each other and often are inconsistent with the 
official definition. Moreover, the official definition is multi-valued for many
dates. In the PDS4 labels, the Cassini Mission phase names were edited for greater 
consistency and clarity. First, short encounters that interrupt longer periods
are defined:

Earth Encounter            1999-230T00:00:00.000         1999-231T00:00:00.000
Jupiter Encounter          2000-365T00:00:00.000         2000-366T00:00:00.000
Phoebe Encounter           2004-163T00:00:00.000         2004-164T00:00:00.000
Saturn Orbit Insertion     2004-183T00:00:00.000         2004-184T00:00:00.000
Titan A Encounter          2004-300T00:00:00.000         2004-301T00:00:00.000
Titan B Encounter          2004-348T00:00:00.000         2004-349T00:00:00.000

2. PDS3 Products Omitted from PDS4 Bundles
------------------------------------------

2a. **PDS3 Software** 

In the original PDS3 delivery, each volume contained a CALIB/ directory, which
contained the calibration files that are now included in the PDS4 calibration
collection. Another subfolder SOFTWARE/CALIB/ contained the software and associated 
input files that were used to generate the calibration data. PDS will not support 
or maintain software in the archive, and so those files are not included in this PDS4 
bundle; instead, they are available via the linked Source_Product_External reference 
for the calibration software in bundle.lblx.

Similarly, the geometry values included in the data object labels were computed
using the software contained in the GEOMETRY_ENGINE.PRO file located under the PDS3 
SOFTWARE/GEOM directory (and using the NAIF SPICE software library, 
https://naif.jpl.nasa.gov/naif/toolkit.html), which are available via the linked 
Source_Product_External reference for the geometry software in bundle.lblx. 

Likewise, the IDL routines to load UVIS PDS3 data and label files into an IDL 
session are provided under the PDS3 SOFTWARE/READERS directory, which are available 
via the linked Source_Product_External reference for the readers software in bundle.lblx.

Note there is a Python package named `pyuvis` that provides tools to work with 
Cassini UVIS data (https://github.com/Cassini-UVIS/pyuvis).

2b. **PDS3 CATALOG Documentation**

This PDS4 bundle references the Cassini-Huygens Mission description 
(cassini-huygens-mission-description.txt, named MISSION.CAT in PDS3) and the Cassini
Orbiter instrument host description (cassini-orbiter-instrument-host-description.txt, 
named INSTHOST.CAT in PDS3). Both these documents were largely extracted from the
Cassini Mission Plan Document (D. Seal, 2003) [JPL D-5564]. This bundle also references
the UVIS instrument description (uvis-instrument-description.txt, named UVISINST.CAT). 

Some CATALOG files (like PERS.CAT, PROJREF.CAT, UVISREF.CAT) contain outdated 
details and so have not been migrated to PDS4.

The remaining UVIS CATALOG files: SCALDS.CAT, SCUBEDS.CAT, SSPECDS.CAT, SSSBDS.CAT,
and SWAVDS.CAT have not been included in the PDS4 bundle because their information 
is presented in Section 2 of the Software Interface Specifications (uvis-sis.pdf),
which is archived in the document collection.


3. Miscellaneous
----------------

The 'occultation_port_state' attribute (from the Cassini mission dictionary) is omitted 
in all FUV PDS4 labels (all FUV PDS3 labels stated OCCULTATION_PORT_STATE = "N/A"). 
EUV PDS4 labels include the occultation_port_state attribute, as either OPEN or CLOSED.
